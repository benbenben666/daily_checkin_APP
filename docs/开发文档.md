**一条防坑规则（v1.3 新增，来自真实事故）**：

> **3. 任何新增的拦截器 / 过滤器，以及任何对 `/api/**` 的访问限制，都必须先放行 CORS 预检请求**（`CorsUtils.isPreFlightRequest(request)` → 直接 `return true`）。

## 1. 项目概述

### 1.1 定位

一个**公司内部的任务发布与执行平台**。公司管理层可以发布任务，员工执行任务并提交成果，所有过程留痕可查。

### 1.2 核心功能

| 模块 | 功能 |
|---|---|
| 账号 | 手机号注册登录；系统管理员由后台手工指定 |
| 公司 | 创建公司（自动成为创始人）；凭邀请码申请加入；解散公司 |
| 成员 | 申请与审批；角色管理；移除成员；拉黑成员 |
| 任务 | 发布任务（全局/指定）；限时控制；抢单与指派；完成提交；超时补交；取消 |
| 附件 | 任务详情配图、完成提交图片（阿里云 OSS） |
| 记录 | 任务全量留痕，按角色控制可见范围 |

### 1.3 两层多租户结构

```
一人多公司  ——  同一个用户可以在多家公司里有身份
一公司多人  ——  一家公司有多名成员
身份独立    ——  张三可以是 A 公司的创始人，同时是 B 公司的员工，
                同时还是系统里的普通用户
```

## 2. 术语表

| 术语 | 含义 |
|---|---|
| 系统角色 | `user.system_role`：用户在整个系统中的身份（USER / ADMIN） |
| 公司角色 | `user_company.company_role`：用户在**某一家公司内**的身份（FOUNDER / MANAGER / EMPLOYEE） |
| 全局任务 | `task_type = GLOBAL`，全公司成员都可执行，先到先得（抢单式） |
| 指定任务 | `task_type = ASSIGNED`，只能由被指派人执行，可指派多人 |
| 参与 | 员工与某个任务的关联关系：全局任务 = 我抢到并完成；指定任务 = 我被指派 |
| 拉黑 | 公司层面永久拒绝某用户加入，记录在 `company_blacklist` |
| 超时完成 | 任务已过 `deadline_at` 之后才提交完成，`is_late = 1` |

## 3. 角色与权限

### 3.1 系统级角色

| 角色 | 说明 | 获取方式 |
|---|---|---|
| `USER` | 普通用户 | 注册即得（数据库默认值） |
| `ADMIN` | 系统管理员（开发者级） | **只能手工改库**，注册接口不提供 |

**`ADMIN` 权限范围**（"什么都能做，直接就是开发者"）：

- 添加 / 删除管理员
- 删除用户、修改任意用户信息
- 解散任意公司（不受"只有创始人能解散"限制）
- 拥有独立的前端页面

### 3.2 公司级角色

| 角色 | 发布任务 | 审批申请 | 拉黑 | 移除成员 | 取消任务 | 解散公司 | 主动退出公司 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| `FOUNDER` 创始人 | ✅ | ✅ 全部 | ✅ | ✅ | ✅ | ✅ 仅本公司 | ❌（须先解散，见 M-13） |
| `MANAGER` 管理者 | ✅ | ✅ 仅员工申请 | ✅ | ✅ | ✅ | ❌ | ✅ |
| `EMPLOYEE` 员工 | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |
| `ADMIN` 系统管理员 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ 任意公司 | ✅（以其在公司的成员身份） |

> **M-13「主动退出公司」是「对自己」的操作**（`POST /api/companies/{id}/leave`，无请求体）：创始人调用返回 409「创始人不能退出公司，请先解散公司」（否则公司会失去唯一创始人），非在职成员返回 403。落地细节见 7.12。

### 3.3 谁能执行任务

**所有公司成员都可以执行任务**，包括创始人和管理者：

- 全局任务：全公司成员（含创始人和管理者）都能抢
- 指定任务：创始人和管理者之间**可以互相指派**

### 3.4 任务可见性

任务的可见性由**两个彼此独立的维度**共同决定，不要混淆：

| 维度 | 字段 | 决定什么 | 取值 |
|---|---|---|---|
| **可见范围** | `task.visibility` | **谁能看见**这个任务 | `PUBLIC` 全部人可见 / `RESTRICTED` 仅指定人可见 |
| **任务类型** | `task.task_type` | **谁能执行**这个任务 | `GLOBAL` 全公司可抢 / `ASSIGNED` 仅被指派人 |

四个组合都成立：

| 组合 | 效果 |
|---|---|
| `GLOBAL` + `PUBLIC` | 全公司可见、全公司可抢（最典型的"抢单任务"） |
| `GLOBAL` + `RESTRICTED` | 只有白名单能看见，看见的人都能抢 |
| `ASSIGNED` + `PUBLIC` | 全公司可见，但只有被指派人能点完成 |
| `ASSIGNED` + `RESTRICTED` | 只有白名单可见，且只有被指派人能执行 |

**除了任务级的可见范围，还有一层人级的数据范围**：

| 视角 | 数据范围 |
|---|---|
| 创始人 / 管理者 / 系统管理员 | 本公司**全部**任务（含所有历史记录） |
| 员工（待抢视图） | 通过可见性校验 **且**（待抢的全局任务 **或** 指派给自己的任务） |
| 员工（历史视图） | 通过可见性校验 **且**（自己完成过 **或** 指派给自己的任务） |

**可见性校验**：`visibility = 'PUBLIC'` **或** 我在 `task_viewer` 白名单里 **或** 我是被指派人 **或** 我是发布者本人。

> 被指派人**不需要**重复写进 `task_viewer` —— 查询时自动可见，避免同一份名单在两处维护。
>
> **「任务详情」的放行口径与列表完全一致**（v1.3 修复）：系统管理员 / 本公司创始人·管理者直接放行，其余人走上面的可见性校验。此前详情少放了「管理者」与「发布者」，管理者在列表里看得见却点不进详情（403），发布者也打不开自己发的 `RESTRICTED` 任务。

## 4. 功能需求

### 4.1 账号

| 编号 | 需求 |
|---|---|
| A-1 | 用户以**手机号**注册，手机号全局唯一，一个手机号只能有一个账号 |
| A-2 | 密码加密存储，绝不存明文 |
| A-3 | 注册产生的新用户系统角色固定为 `USER` |
| A-4 | **管理员无法通过注册成为**，只能由人工修改数据库 |
| A-5 | 「删除用户」为软删除（`status = 0`），不做物理删除（见 6.5） |

### 4.2 公司

| 编号 | 需求 |
|---|---|
| C-1 | 任何用户都可以创建公司，创建者自动成为该公司**创始人** |
| C-2 | 公司 ID 由数据库自增保证唯一 |
| C-3 | 公司**名称允许重名** |
| C-4 | 每家公司有唯一的**邀请码**，是加入公司的唯一凭据（因为名称可重名，无法定位） |
| C-5 | 解散公司：**仅创始人可解散本公司**；管理者不可以；**系统管理员可解散任意公司** |

### 4.3 成员

| 编号 | 需求 |
|---|---|
| M-1 | 用户凭**邀请码**申请加入公司 |
| M-2 | 申请时选择身份：`MANAGER` 或 `EMPLOYEE`（**不可申请 `FOUNDER`**） |
| M-3 | 同一用户对**同一家公司**每天最多申请 **3 次** |
| M-4 | 有一条待审批申请时，不能再申请同一家公司 |
| M-5 | 撤回、被拒、通过、待审批**全部计入**每日 3 次限额 |
| M-6 | 被拒绝后可以再次申请（受 M-3 限额约束） |
| M-7 | **申请历史完整保留**，可追溯被拒几次 |
| M-8 | 审批权限：申请 `MANAGER` 只能由**创始人**审批；申请 `EMPLOYEE` 由创始人和管理者共同审批；**公司当前没有管理者时一律回退给创始人** |
| M-9 | 创始人/管理者可**拉黑**成员；拉黑后该用户**永久**不能申请该公司 |
| M-10 | 被拉黑者若**在职**，同时被踢出公司；若**非在职**，仅禁止申请 |
| M-11 | 若被拉黑者有**待审批**申请，该申请立即变为「已拒绝」（申请人看到的是被拒绝，不暴露拉黑事实） |
| M-12 | 创始人/管理者可**移除**在职成员（不拉黑） |
| M-13 | 用户可**主动退出**公司 |
| M-14 | 退出/被移除后可重新申请；审批通过时复用原成员记录行 |
| M-15 | 「主动退出 / 被移除 / 被拉黑」三种离职方式必须可区分 |

### 4.4 任务

| 编号 | 需求 |
|---|---|
| T-1 | 创始人、管理者可发布任务 |
| T-2 | 任务包含**标题**和**详情**；详情支持**上传图片** |
| T-3 | 任务可设置**限时时长**，范围 **5 分钟 ~ 30 天**（5 ~ 43200 分钟） |
| T-4 | 任务类型一：**全局任务**（`GLOBAL`）—— 全公司成员（含创始人和管理者）都可执行，**先到先得，一人完成即结束** |
| T-5 | 任务类型二：**指定任务**（`ASSIGNED`）—— 指派给指定成员，**可指派多人**；创始人和管理者之间可互相指派 |
| T-6 | 任务状态：`PENDING` 未完成 / `EXPIRED` 已超时 / `COMPLETED` 已完成 / `CANCELLED` 已取消 |
| T-7 | 完成任务时可提交**文字描述**、**图片**，也**允许什么都不填**直接提交 |
| T-8 | **超时后是否允许补交**由发布时设置的 `allow_late_submit` 开关控制，**默认允许**；补交窗口长度 **等于限时时长本身**；超时提交的内容标记为「超时完成」 |
| T-9 | 取消任务：**本公司创始人和管理者**都可以执行 |
| T-10 | 所有任务**全部留痕**，不做物理删除 |
| T-11 | 任务的**可见范围**可设为「全部人可见」或「指定人可见」；选后者时必须指定可见人白名单 |
| T-12 | 任务发布后**可修改**：发布者和具有管理权限的人（创始人 / 管理者）都可以改，且**所有字段都可改** —— 包括任务类型（`GLOBAL` ↔ `ASSIGNED` 可以互改）和可见范围。发布者这条路径要求**其本人仍是该公司在职成员**（被移除/拉黑后不能再改自己的历史任务） |
| T-13 | 任务可见性按 3.4 的规则控制 |
| T-14 | **已完成 / 已取消的任务不能编辑**（返回 409）；编辑时把 `ASSIGNED` 任务的被指派人清空、或把 `RESTRICTED` 任务的可见人清空都会被拒绝（400，见 6.15） |
| T-15 | 发布/编辑时，被指派人、可见人**必须全部是该公司当前在职成员**；单次最多 200 个 ID，自动去重；单张任务的配图最多 20 张 |

### 4.5 附件

| 编号 | 需求 |
|---|---|
| F-1 | 图片存储使用**阿里云 OSS** |
| F-2 | 数据库只存 OSS `object_key`，不存完整 URL |
| F-3 | 图片分两类：任务详情配图（`DETAIL`）、完成提交图（`SUBMIT`） |

## 6. 关键设计决策

### 6.1 用中间表而非在 `user` 上加 `company_id`

一个人属于多家公司，挂在 `user` 上无法表达。中间表还承载了**关系自身的属性**（角色、加入时间、离职时间），这是多对多建模的标准做法。

### 6.2 「申请」为什么必须独立成表

申请和成员关系是**两种生命周期完全不同的实体**：

| | 成员关系 | 申请 |
|---|---|---|
| 性质 | 长期状态 | 一次性事件 |
| 生命周期 | 加入 → 在职 → 离职 | 提交 → 审批 → 终结 |
| 独有属性 | 加入时间、离职时间 | 申请角色、审批人、审批时间、拒绝理由 |

若塞进 `user_company`：所有在职员工的审批字段永远是 NULL（语义脏）；「被拒绝」与「已退出」共用同一状态值无法区分；`uk_user_company` 只允许一行，会丢失「被拒 3 次」的历史。

### 6.3 「拉黑」为什么必须独立成表

- 一个**从没加入过**公司的人也能被拉黑 → `user_company` 里没有行可改
- 一个**在职**的人也能被拉黑 → 与 `uk_user_company` 唯一键冲突
- 拉黑记录本身携带审计信息（谁拉的、什么时候、为什么）

### 6.4 生成列 + 唯一索引：MySQL 缺失的「部分唯一约束」

MySQL 不支持 PostgreSQL 的 `UNIQUE ... WHERE 条件`，但**唯一索引允许多个 NULL**。在唯一索引前垫一个生成列，即可实现"只对满足条件的行做唯一约束"：

| 业务需求 | 生成列表达式 | 唯一索引 |
|---|---|---|
| 每公司最多一个创始人 | `IF(company_role='FOUNDER', 1, NULL)` | `(company_id, founder_only)` |
| 每人每公司最多一条待审批 | `IF(status='PENDING', 1, NULL)` | `(user_id, company_id, pending_only)` |

非目标行算出 `NULL`，NULL 在唯一索引中互不冲突 —— 于是"非目标行可以有任意多条，目标行只能有一条"。

### 6.5 「删除用户」只能是软删除

`user.id` 被以下位置引用：`user_company`、`join_application`（申请人 + 审批人）、`company_blacklist`（被拉黑者 + 操作人）、`task`（发布人 + 完成人 + 取消人）、`company.dissolved_by`。外键默认 `RESTRICT`，物理删除必然失败。

更重要的是：**硬删除会破坏任务历史**（"谁完成的"变成空白），与"所有任务都要留痕"直接冲突。

**因此"删除用户" = `UPDATE user SET status = 0`（禁用）**，登录时校验 `status = 1`。

### 6.6 约束分层：哪些交给数据库，哪些交给业务层

| 约束 | 由谁保证 | 理由 |
|---|---|---|
| 手机号唯一 | **数据库** | 并发下只有唯一索引靠得住 |
| 不能重复加入同一公司 | **数据库** | 同上 |
| 每公司最多一个创始人 | **数据库** | 业务层容易漏 |
| 拉黑永久生效 | **数据库** | "永久"语义放数据库最稳 |
| 同公司只能有一条待审批 | **数据库** | 防止刷爆审批队列 |
| 枚举值合法 | **数据库**（CHECK） | 挡住 `'admin'`、`'ADMN'` 等脏值 |
| 状态与附属字段一致 | **数据库**（CHECK） | 如"已完成却没有完成人" |
| 引用完整性 | **数据库**（外键） | 防止孤儿数据 |
| **每天最多申请 3 次** | **业务层** | 见下 |
| 谁能审批哪种申请 | **业务层** | 权利矩阵 |
| 拉黑时是否踢人 | **业务层** | 动作编排 |
| 完成任务时的抢单原子性 | **数据库**（条件 UPDATE + 行锁） | 见 6.7 |

**为什么「一天 3 次」不放数据库？** 可以写成触发器，但触发器同样防不住并发（两个请求同时 COUNT 到 2 然后都插入）。既然数据库层做不到完全正确，就不值得为它增加触发器的维护成本。业务层 COUNT 一次即可，偶发超到 4 次无实质危害。

**判断标准**：这是**数据正确性**问题，还是**频率**问题？前者交给数据库，后者业务层足够。

### 6.7 ⭐ 抢单的原子性（本项目最重要的一点）

全局任务"只要有人做就可以"，意味着**两个人可能同时点完成**。

**绝对不能这么写**：

```java
Task t = taskMapper.selectById(id);
if ("PENDING".equals(t.getStatus())) {          // ← 两个人同时读到 PENDING
    taskMapper.updateStatus(id, "COMPLETED");   // ← 两个人都更新成功
}
```

**正确做法是一条带条件的 UPDATE，靠 InnoDB 行锁保证原子性**（完整 SQL 见 7.4）。判断结果只看影响行数：`1` = 抢到，`0` = 被别人抢先 / 已取消 / 无权限。

这一个 `UPDATE` 同时完成「检查权限 + 检查状态 + 写入完成」，中间没有缝隙给并发钻，**不需要分布式锁，也不需要 `synchronized`**。

### 6.8 「已超时」与「超时完成」

`status` 的四个值性质并不相同：

| 状态 | 性质 | 谁来改 |
|---|---|---|
| `PENDING` | 事实 | 发布时写入 |
| `COMPLETED` | **人的决策** | 执行人提交 |
| `CANCELLED` | **人的决策** | 管理者 |
| `EXPIRED` | **时间的函数** | 没人点它，它自己会到 |

由于用户允许**超时补交**，状态机变成：

```
                    ┌──按时完成──> COMPLETED (is_late = 0)
                    │
PENDING ────────────┼──超时──> EXPIRED ──补交──> COMPLETED (is_late = 1)
                    │
                    └──取消──> CANCELLED
```

**「是否超时完成」用生成列推导，而不是新增第 5 个状态值**：

```sql
`is_late` TINYINT GENERATED ALWAYS AS (
    IF(`completed_at` IS NOT NULL AND `completed_at` > `deadline_at`, 1, 0)
) STORED
```

理由：它**完全由 `completed_at` 和 `deadline_at` 决定**，是推导值而非独立事实。用生成列意味着：

1. **不可能标错** —— 不存在"代码里判断分支写反"的情况
2. **不需要额外写入逻辑** —— 提交时只管写 `completed_at`
3. **与 `founder_only`、`pending_only` 一脉相承** —— 全设计统一遵循"推导出来的事实不手工维护"

**边界**：正好卡在截止时刻提交算**按时**（用 `>` 而非 `>=`）。

### 6.9 图片表为什么只有一张（带 `image_type`）

任务有两个地方能传图：发布时的详情配图、完成时的提交图。它们**生命周期与所属任务完全一致**，所以一张表 + 一个类型列即可。

**与 6.2 / 6.3 的区别**：那两张表独立是因为**生命周期不同**；图片只是**用途不同**。判断标准是生命周期，不是"看起来像不像"。

### 6.10 图片存 OSS `object_key` 而非完整 URL

完整 URL 里的域名会变（换 CDN、绑自定义域名、切内外网 endpoint、加防盗链签名）。存完整 URL 一旦域名变更就要**批量 UPDATE 全表**；存 key 则只需改一行拼接代码。

### 6.11 「可见范围」与「任务类型」是两个正交维度

最初的设计里只有 `task_type`，它被迫同时承担两个职责。加上可见范围后必须拆开：

| 维度 | 决定什么 | 字段 |
|---|---|---|
| **执行权限** | 谁能**点完成** | `task_type` |
| **数据可见性** | 谁能**看见** | `visibility` |

**为什么不能合并成一个字段？** 因为四种组合都有真实业务含义（见 3.4）："指定任务但全公司可见"是常见的公示场景；"全局任务但只有部分人可见"则是有针对性的抢单。

**实现上的一个关键细节**：被指派人**不必**写进 `task_viewer`。可见性查询把"是否被指派"作为独立条件判断，而不是在写入时把指派人同步进白名单 —— 后者会让同一份名单存在两处，需要时刻保持一致，正是本项目一直在避免的问题（同 6.2 / 6.3 的思路）。

### 6.12 三个时间列全部由数据库算，应用层不碰

你的原话是：*"任务截止时间是从开始时自动开始算的，选五分钟就在发布那一刻自动算截止"*。

这句话说明**截止时间不是独立字段，而是 `发布时间 + 限时时长` 的推导结果**。既然如此，就不该交给应用层去算：

```
time_limit_minutes   ← 用户唯一需要填的时间字段
deadline_at          = created_at + time_limit_minutes        （生成列）
late_deadline_at     = deadline_at + time_limit_minutes       （生成列）
is_late              = completed_at > deadline_at             （生成列）
```

**好处**：

1. 应用层**根本没有写入截止时间的机会**，也就不可能写错
2. 编辑任务时只需改 `time_limit_minutes`，两个截止时间自动跟着变
3. 与 6.4 的 `founder_only`、`pending_only` 一致 —— 推导出来的事实不手工维护

**代价**：不能脱离时长单独调整截止时间。将来若需要"延长截止但保持时长不变"，要把 `deadline_at` 改回普通列。

**补交窗口语义**：你说的"默认补交的时间就是等同于任务完成时间限制"，落地为 **补交窗口长度 = 限时时长本身**。

**实测验证**（MySQL 8.0.44 临时表，用最终定义跑的真实结果）：

| 发布时刻 | 限时 | 完成截止 | 补交截止 | 完成时刻 | `is_late` |
|---|---|---|---|---|---|
| 14:00 | 30 分钟 | 14:30 | 15:00 | 14:20 | **0** 按时 |
| 14:00 | 30 分钟 | 14:30 | 15:00 | **14:30 整** | **0** 卡点算按时 |
| 14:00 | 30 分钟 | 14:30 | 15:00 | 14:45 | **1** 超时完成 |
| 14:00 | 30 分钟 | 14:30 | 15:00 | 未完成 | 0 |
| 14:00 | 5 分钟 | 14:05 | 14:10 | — | — |
| 14:00 | 43200 分钟（30 天） | 10-23 14:00 | 11-22 14:00 | — | — |

### 6.13 时限判定写进 SQL，不再依赖定时任务

`complete` 这条条件 UPDATE 原来只判断 `status IN ('PENDING','EXPIRED')`，"是否还在补交窗口内"靠 `TaskExpireScheduler` 每分钟把 `PENDING` 刷成 `EXPIRED` 间接生效。这有两个问题：**最长 60 秒的空窗**（刚过截止时间、还没被刷成 `EXPIRED` 的任务仍可提交），以及**定时任务一旦停摆就完全失效**（任务永远停在 `PENDING`，于是永远可以提交）。

v1.3 把时限判定直接写进 SQL（完整语句见 7.4）：

```sql
AND (NOW() <= t.`deadline_at`
     OR (t.`allow_late_submit` = 1 AND NOW() <= t.`late_deadline_at`))
```

`TaskExpireScheduler` 保留（它负责把状态刷成 `EXPIRED`，让列表/详情显示正确），但**它不再是正确性的必要条件** —— 它慢了一分钟、或者整个停摆，都不影响"现在能不能提交"。

**一个有意的副作用**：`allow_late_submit = 0` 的任务，即使定时任务还没把它刷成 `EXPIRED`、状态仍是 `PENDING`，只要过了 `deadline_at` 就立即不能提交。旧写法"状态还是 `PENDING` 就放行"会额外给出最多 60 秒的提交窗口。

### 6.14 抢单必须同时满足可见性

`complete` 此前只校验状态、时限和执行权限（`task_type` / 是否被指派人），**不校验可见性**。于是只要枚举出 `task.id`，任何人都能抢走一条自己看不见的 `GLOBAL + RESTRICTED` 任务 —— 白名单外的人本来不该知道它存在，却能凭 ID 抢单，并在抢单成功后从响应里把标题、详情一并拿到。

v1.3 在同一条 UPDATE 里补上可见性条件：

```sql
AND (t.`visibility` = 'PUBLIC'
     OR ta.`id` IS NOT NULL                                   -- 我是被指派人
     OR EXISTS (SELECT 1 FROM `task_viewer` tv
                WHERE tv.`task_id` = t.`id` AND tv.`user_id` = #{userId}))
```

这与 3.4 的可见性口径完全一致，也再次体现 6.7 的价值：**每加一条业务规则，只是往同一条 UPDATE 的 WHERE 里再加一个 AND，不会引入新的竞态窗口。**

### 6.15 编辑任务：用「合并后的生效值」校验，并且不允许把关联清空

编辑接口是"部分更新"（字段为 `null` 表示"不改"），由此产生两个坑，v1.3 一并修掉：

| 坑 | 后果 | 修复 |
|---|---|---|
| **用请求值校验、却用生效值落库** | 对一条已存在的 `ASSIGNED` 任务传 `assigneeIds: []`（`taskType` 传 `null`）时，"指定任务必须有被指派人"的校验因为 `taskType == null` 被跳过，而落库时被指派人被清空 → `task_type = 'ASSIGNED'` 却没有指派行，**这条任务永远无法被任何人完成**（抢单条件要求 `task_assignee` 命中） | 校验改用合并后的生效值：`finalType = req.taskType ?? task.taskType`、`finalVisibility = req.visibility ?? task.visibility`；并**显式拒绝**清空 `ASSIGNED` 的被指派人、清空 `RESTRICTED` 的可见人（400） |
| **空请求体** | 传 `{}` 时 MyBatis 的 `<set>` 会拼出 `UPDATE task WHERE id = ?` 这种非法 SQL | 所有 task 字段都为 `null` → **跳过 UPDATE**；task 字段与关联数据都为 `null` → 返回 400「没有需要修改的字段」 |

**另外**：`COMPLETED` / `CANCELLED` 的任务不能编辑（409）—— 这是原有代码就有的行为，v1.3 之前文档漏写，现已补进 4.4 T-14。发布者这条路径还新增了「必须是当前在职成员」的校验（见 4.4 T-12）：被移除/拉黑后不能再改自己的历史任务，否则可以靠改 `time_limit_minutes` 来延长截止时间。

### 6.16 全局异常有意保持 HTTP 状态码 200

`GlobalExceptionHandler` 把所有异常都转成统一响应体，**HTTP 状态码恒为 200**，错误码放在响应体的 `code` 里（`0` 成功，非 0 为 400/401/403/404/405/409/429/500 等语义码）。

**为什么**：前端 `src/api/request.js` 只读 `body.code`（它完全不检查 HTTP 状态码）。如果后端改成真实 HTTP 状态码，前端拿到的 `body` 会变成 Spring 容器的默认错误结构（`{timestamp, status, error, path}`）而不是 `{code, message, data}`，所有错误提示都会退化成"请求失败"。

**这是一份契约**：将来若要改成真实 HTTP 状态码，必须**同时**改前端解析逻辑并更新 8.1。

v1.3 的改进是**分类**——此前 404 / 405 / 请求体非法 JSON / 唯一键冲突 / 字段超长全部被压成 `code=500`「服务器内部错误」：

| 异常 | 现在的 `code` | 消息 |
|---|---|---|
| `BizException` | 自带 | 业务文案 |
| 请求体不是合法 JSON | 400 | 请求体格式不正确 |
| 缺必填参数 / 参数类型不对（如路径 `id` 传非数字） | 400 | 请求参数不合法 |
| 数据层约束（外键 / CHECK / NOT NULL / 字段超长） | 400 | 提交的数据不符合要求 |
| 接口不存在 | 404 | 接口不存在 |
| 请求方法不被支持 | 405 | 请求方法不被支持 |
| 唯一键冲突 | 409 | 操作冲突或重复提交，请刷新后重试 |
| 登录失败次数过多 | 429 | 登录失败次数过多，请 N 分钟后再试 |
| 其他 | 500 | 服务器内部错误 |

### 6.17 「每天最多 3 次申请」用行锁串行化（对 6.6 的修正）

6.6 说"频率问题交给业务层足够"，这对**限流强度**成立，但 v1.3 发现原实现连"最多 3 次"都不保证：`countToday` 与 `hasPending` 都是**先查后写**，两个并发请求可以同时读到 `count = 2`、同时通过校验、同时插入，最终变成 4 条。

修复方式不是加触发器，而是**把同一用户的申请串行化**：`join` 加 `@Transactional`，并在计数之前先 `SELECT id FROM user WHERE id = ? FOR UPDATE`（`UserMapper.lockById`）锁住本人这一行。同一用户的并发申请排队执行，不同用户之间互不影响。

**为什么锁 `user` 行而不是 `join_application` 的行**：要防的是"同一用户在同一家公司重复申请"，而计数对象是**还不存在的行**（对不存在的行加锁要依赖间隙锁，语义复杂且与索引相关）；锁一个必然存在的用户行最简单可靠。

> 数据库层的 `uk_one_pending`（6.4）依然是最后一道防线：它挡的是"两条待审批"，但挡不住"一天 4 次"（这 4 次里可以有撤回、被拒、通过）。

### 6.18 M-13 主动退出：把 `leave_type = 1` 真正落地

`user_company.leave_type` 从设计之初就有三个取值（1-主动退出 / 2-被移除 / 3-被拉黑），但 v1.3 之前**全项目从未写入过 `leave_type = 1`** —— M-15「三种离职方式必须可区分」实际只落实了 2/3，库里永远不存在"主动退出"的行。

v1.3 补上接口 `POST /api/companies/{id}/leave` 与 `UserCompanyMapper.leave`（`SET status=0, leave_type=1, left_at=NOW() WHERE ... AND status=1`），三种方式终于可区分。

**规则与理由**：

- **创始人不能退出**（409「创始人不能退出公司，请先解散公司」）—— `uk_one_founder` 只保证每家公司**最多**一个创始人，没有任何约束保证**至少**一个；允许创始人退出会造出一家**没有创始人**的公司（无人能解散公司、无人能审批管理者申请），比"要求他先解散"更糟
- **非在职成员返回 403** —— `where status = 1` 本身只会写 0 行，但显式判定能给出可读提示

### 6.20 ⭐ CORS 预检必须放行（否则前端在浏览器里整体不可用）

这是本轮**最隐蔽也最严重**的一个 bug，值得单独成节。

**现象**：`OPTIONS /api/companies/10/tasks`（带 `Origin: http://localhost:5173`）返回 **HTTP 500**，堆栈是 `BizException: 未登录 at AuthInterceptor.preHandle(...)`。

**原因**：`AuthInterceptor` 注册在 `/api/**` 上、且对**所有**请求都要求 `Authorization` 头。但 CORS 预检请求是**浏览器自动发出的 `OPTIONS`**，按 CORS 规范**不携带** `Authorization`（预检只声明"将要使用哪些头"，不带头的值）—— 于是预检被登录校验挡下，响应里也就没有 `Access-Control-Allow-*`。

**为什么影响是"整体不可用"而不是"偶发失败"**：前端每个请求都带 `Authorization`，且 `Content-Type: application/json` 也属于"非简单请求"的触发条件，所以**每一个跨域请求都会先发预检**。预检失败 → 浏览器直接拒绝发起真实请求（真实请求根本到不了后端）→ 前端所有接口调用全部失败。

**为什么之前一直没暴露**：前端从未真正在浏览器里跑起来过（首版页面写完即进入本轮修复），只做后端 curl/Postman 测试的话永远不会碰到预检。

**修复**（`AuthInterceptor.preHandle` 开头）：

```java
// CORS 预检请求（OPTIONS）由浏览器自动发出，不携带 Authorization 头，必须直接放行
if (CorsUtils.isPreFlightRequest(request)) {
    return true;
}
```

**验证结果（本轮 HTTP 冒烟测试）**：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `OPTIONS /api/companies/10/tasks`（`Origin: http://localhost:5173`） | **500**（未登录） | **200** + 完整的 `Access-Control-Allow-Origin / Methods / Headers` |
| `OPTIONS /api/tasks/3/complete` | 500 | 200 |
| `OPTIONS` 带 `Origin: http://evil.example.com`（非法来源） | — | **403**（CORS 收窄仍然生效，放行预检不等于放开跨域） |

**这不是一次性的修补，而是一条约束**：预检请求的放行必须发生在"任何鉴权/限流/日志拦截器"之前。以后新增拦截器、Filter、Spring Security 配置时，都要遵循维护约定里的第 3 条 —— **否则前端在浏览器里会整体不可用，且后端只留下一条容易被忽视的"未登录"日志**。

## 7. 核心业务流程

### 7.1 注册

```sql
-- 注意：不写 system_role，由数据库默认值给出 'USER'
INSERT INTO `user` (`phone`, `password`, `nickname`) VALUES (?, ?, ?);
```

### 7.2 创建公司

```
1. INSERT company (name, invite_code, ...)        -- 生成唯一邀请码
2. INSERT user_company (user_id, company_id, 'FOUNDER', status=1)
   ↑ 与上一步在同一事务中
```

`uk_one_founder` 会在数据库层保证每家公司不会出现第二个创始人。

> **v1.3 实现细节**：`CompanyMapper.insert` 带 `useGeneratedKeys="true" keyProperty="id"`，插入后主键**直接回填到实体**，第 2 步用回填的 ID 即可。此前是"insert 之后再 `selectByInviteCode` 回查一次拿 ID"，多一次查询、也多一个"邀请码被并发改掉"的理论风险。注意邀请码本身仍是**先随机生成、再查一次防撞**（`invite_code` 的 `uk_invite_code` 是最终兜底）。

### 7.3 申请加入公司

```
1. 查 company_blacklist  → 有记录 → 拒绝
2. 查 user_company (status=1) → 已是成员 → 拒绝
3. SELECT id FROM user WHERE id = ? FOR UPDATE   ← v1.3 新增：锁本人用户行，把并发申请串行化
4. 查今日申请次数（同公司）≥ 3 → 拒绝
5. 查是否已有 PENDING → 有 → 拒绝
6. INSERT join_application (status='PENDING', apply_role=?)
```

> 第 3 步（`UserMapper.lockById`）是 v1.3 补的：第 4、5 步都是"先查后写"，没有这把行锁时并发请求可以绕过"每天 3 次"限制。理由见 6.17。整个 `join` 是 `@Transactional`。

今日次数查询（**注意不要在列上加函数**）：

```sql
SELECT COUNT(*) FROM `join_application`
WHERE `user_id` = ? AND `company_id` = ?
  AND `created_at` >= CURDATE()
  AND `created_at` <  CURDATE() + INTERVAL 1 DAY;
-- 不加 status 条件 → 撤回、拒绝、通过、待审批全部计入 3 次
```

### 7.4 完成任务 / 超时补交

```sql
UPDATE `task` t
LEFT JOIN `task_assignee` ta ON ta.`task_id` = t.`id` AND ta.`user_id` = :me
SET t.`status`         = 'COMPLETED',
    t.`completed_by`   = :me,
    t.`completed_at`   = NOW(),
    t.`submit_content` = :content
WHERE t.`id` = :taskId
  AND t.`status` IN ('PENDING', 'EXPIRED')   -- 未完成或已超时（已取消/已完成不能再提交）
  AND (NOW() <= t.`deadline_at`                       -- 未过完成截止：随时可提交
       OR (t.`allow_late_submit` = 1                  -- 已过截止：开关必须打开
           AND NOW() <= t.`late_deadline_at`))        -- 且仍在补交窗口内（见 6.13）
  AND (t.`task_type` = 'GLOBAL'              -- 全局任务谁都能做
       OR ta.`id` IS NOT NULL)               -- 指定任务只有被指派人能做
  AND (t.`visibility` = 'PUBLIC'             -- 可见性：看不见的任务不能抢（见 6.14）
       OR ta.`id` IS NOT NULL                -- 我是被指派人
       OR EXISTS (SELECT 1 FROM `task_viewer` tv
                  WHERE tv.`task_id` = t.`id` AND tv.`user_id` = :me));
```

`is_late` 不需要手工写入，由数据库自动推导。

`LEFT JOIN task_assignee` 是为了让"指定任务只有被指派人能做"这个校验也在同一条语句内完成，否则先查一次指派表就又产生了竞态窗口。

**这条 UPDATE 同时完成四件事**（这也是 6.7 的核心理由）：检查状态、检查时限与补交窗口、检查执行权限、检查可见性。**影响 1 行 = 抢到，0 行 = 被别人抢先 / 已取消 / 超出补交时限 / 无权执行 / 看不见该任务** —— 服务层只根据影响行数返回统一的 409 提示，不需要（也无法）区分具体原因。

### 7.5 取消任务

```sql
UPDATE `task`
SET `status` = 'CANCELLED', `cancelled_by` = ?, `cancelled_at` = NOW(), `cancel_reason` = ?
WHERE `id` = ? AND `status` IN ('PENDING', 'EXPIRED');   -- 已完成/已取消的不能再取消
```

### 7.6 定时标记超时（Spring `@Scheduled`，每分钟）

```sql
UPDATE `task` SET `status` = 'EXPIRED'
WHERE `status` = 'PENDING' AND `deadline_at` < NOW();
```

> ⚠️ 定时任务存在最长一分钟的延迟。
>
> **v1.3 起，7.4 的完成逻辑不再依赖这个定时任务的及时性** —— "是否还在时限/补交窗口内"已直接写进那条 UPDATE 的 WHERE（见 6.13）。本定时任务现在的职责只有一个：**把状态刷成 `EXPIRED`，让列表与详情的状态显示正确**（`PENDING` → `EXPIRED` 是给人看的状态迁移；"能不能提交"由 SQL 自己判定）。定时任务停摆只会导致状态显示滞后，不会导致"过期还能提交"。

### 7.7 审批

```sql
-- 通过（事务）
-- 前置校验（v1.3 新增）：公司未解散、申请人未被拉黑
--   公司已解散 → 409「公司已解散，无法审批」
--   申请人已被拉黑 → 403「该用户已被拉黑，无法通过申请」
--   否则 upsert 会把一个已解散公司的成员行恢复成在职
START TRANSACTION;
UPDATE `join_application`
SET `status` = 'APPROVED', `reviewer_id` = ?, `reviewed_at` = NOW()
WHERE `id` = ? AND `status` = 'PENDING';     -- 影响 0 行说明已被他人处理，回滚

INSERT INTO `user_company` (`user_id`, `company_id`, `company_role`, `status`, `joined_at`, `left_at`)
VALUES (?, ?, ?, 1, NOW(), NULL) AS new
ON DUPLICATE KEY UPDATE                       -- 曾离职则复用原行，避免撞唯一键
    `company_role` = new.`company_role`,
    `status` = 1, `leave_type` = NULL, `joined_at` = new.`joined_at`, `left_at` = NULL;
COMMIT;

-- 拒绝（v1.3：理由限 200 字，超长返回 400，避免撞 VARCHAR(200) 报 500）
UPDATE `join_application`
SET `status` = 'REJECTED', `reviewer_id` = ?, `reviewed_at` = NOW(), `reject_reason` = ?
WHERE `id` = ? AND `status` = 'PENDING';

-- 申请人撤回
UPDATE `join_application`
SET `status` = 'CANCELLED'
WHERE `id` = ? AND `user_id` = ? AND `status` = 'PENDING';
```

**审批权限判断**（v1.3 修正了此处文档与代码的不符，见下）：

**「公司当前没有管理者时一律回退给创始人」不是一步查询，而是逻辑上的必然结果**：

```sql
-- ⚠️ 设计稿，尚未实现：UserCompanyMapper.hasManager / 对应 XML 存在，但全项目没有任何调用点（见 6.19）
-- 公司当前有没有管理者（走 idx_company_status_role）
SELECT EXISTS (
    SELECT 1 FROM `user_company`
    WHERE `company_id` = ? AND `status` = 1 AND `company_role` = 'MANAGER'
) AS has_manager;
```

**代码里不做这个查询** —— `ApplicationService.checkReviewPermission` 直接用注释说明"无需额外判断"：若公司当前没有在职管理者，审批人**不可能**是 `MANAGER` 角色（`selectActiveRole` 只会返回 `FOUNDER` 或 `null`），"创始人或管理者可批"这条规则自然只剩创始人能满足，结果与专门查一次 `has_manager` 完全一致，因此这一查是多余的。

| 申请身份 | 谁能批 |
|---|---|
| `MANAGER` | 仅创始人 |
| `EMPLOYEE` | 创始人 或 管理者 |
| 公司无管理者 | 一律回退创始人 |

### 7.8 拉黑（在职 / 非在职合并为一条代码路径）

**前置校验**（v1.3 补齐，顺序即代码顺序）：

| 校验 | 失败返回 |
|---|---|
| 公司存在且未解散（`requireCompany`） | 404 / 409 |
| 操作人是本公司创始人/管理者或系统管理员 | 403 |
| `userId` 非空 | 400「缺少被拉黑用户」 |
| 不能拉黑自己 | 400 |
| **被拉黑用户必须真实存在**（v1.3 新增） | 404「被拉黑的用户不存在」—— 此前会直接撞 `fk_bl_user` 外键报 500 |
| `reason` ≤ 200 字（v1.3 新增） | 400 —— 此前超长会撞 `VARCHAR(200)` 报 500 |
| 不能拉黑创始人 | 403 |

```sql
START TRANSACTION;

-- ① 写黑名单（幂等，重复拉黑不报错）
INSERT INTO `company_blacklist` (`company_id`, `user_id`, `operator_id`, `reason`)
VALUES (?, ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE
    `operator_id` = new.`operator_id`,
    `reason`      = new.`reason`;        -- created_at 保留最初拉黑时间

-- ② 踢出公司 —— 只在职时生效，否则影响 0 行
UPDATE `user_company`
SET `status` = 0, `leave_type` = 3, `left_at` = NOW()
WHERE `user_id` = ? AND `company_id` = ? AND `status` = 1;

-- ③ 待审批申请 → 显示为被拒绝（不暴露拉黑事实）
UPDATE `join_application`
SET `status` = 'REJECTED', `reject_reason` = '申请未通过', `reviewed_at` = NOW()
WHERE `user_id` = ? AND `company_id` = ? AND `status` = 'PENDING';

COMMIT;
```

**①+③ 恒执行，② 靠 `WHERE status = 1` 自动变成空操作** —— 所以"在职"和"非在职"两种场景走同一个方法，无需分支。

### 7.9 移除成员（不拉黑）

**前置校验**：操作人是本公司创始人/管理者或系统管理员（403）；不能移除自己（400）；目标必须是本公司在职成员（404）；不能移除创始人（403）。

```sql
UPDATE `user_company`
SET `status` = 0, `leave_type` = 2, `left_at` = NOW()
WHERE `user_id` = ? AND `company_id` = ? AND `status` = 1;
```

### 7.10 解散公司

```sql
-- 创始人只能解散自己的；系统管理员可解散任意
UPDATE `company`
SET `status` = 0, `dissolved_by` = ?, `dissolved_at` = NOW()
```

### 7.11 可见性查询

```sql
-- 创始人 / 管理者 / 系统管理员：本公司全部任务
SELECT * FROM `task` WHERE `company_id` = ?;

-- 员工：待抢视图（可见 且（待抢的全局任务 或 指派给自己））
SELECT * FROM `task` t
WHERE t.`company_id` = ?
  -- ① 可见性校验
  AND (
        t.`visibility` = 'PUBLIC'
     OR EXISTS (SELECT 1 FROM `task_viewer`  tv WHERE tv.`task_id` = t.`id` AND tv.`user_id` = :me)
     OR EXISTS (SELECT 1 FROM `task_assignee` ta WHERE ta.`task_id` = t.`id` AND ta.`user_id` = :me)
  )
  -- ② 数据范围
  AND (
        (t.`task_type` = 'GLOBAL' AND t.`status` = 'PENDING' AND t.`deadline_at` > NOW())
        -- v1.3 新增：已超时但仍在补交窗口内的全局任务必须留在列表里，
        -- 否则任务一超时就消失，员工再也找不到补交入口
     OR (t.`task_type` = 'GLOBAL' AND t.`status` = 'EXPIRED'
         AND t.`allow_late_submit` = 1 AND NOW() <= t.`late_deadline_at`)
     OR EXISTS (SELECT 1 FROM `task_assignee` ta2 WHERE ta2.`task_id` = t.`id` AND ta2.`user_id` = :me)
  );

-- 员工：历史视图（可见 且 我参与过的）
SELECT * FROM `task` t
WHERE t.`company_id` = ?
  AND (
        t.`visibility` = 'PUBLIC'
     OR EXISTS (SELECT 1 FROM `task_viewer`  tv WHERE tv.`task_id` = t.`id` AND tv.`user_id` = :me)
     OR EXISTS (SELECT 1 FROM `task_assignee` ta WHERE ta.`task_id` = t.`id` AND ta.`user_id` = :me)
  )
  AND (
        t.`completed_by` = :me
     OR EXISTS (SELECT 1 FROM `task_assignee` ta2 WHERE ta2.`task_id` = t.`id` AND ta2.`user_id` = :me)
  );

-- 单条任务的可见性校验（进详情页前）
SELECT EXISTS (
    SELECT 1 FROM `task` t
    WHERE t.`id` = ?
      AND (t.`visibility` = 'PUBLIC'
        OR t.`publisher_id` = :me                                          -- 发布者本人（v1.3 补进 SQL）
        OR EXISTS (SELECT 1 FROM `task_viewer`   tv WHERE tv.`task_id` = t.`id` AND tv.`user_id` = :me)
        OR EXISTS (SELECT 1 FROM `task_assignee` ta WHERE ta.`task_id` = t.`id` AND ta.`user_id` = :me))
) AS can_view;

-- 统计超时完成
SELECT COUNT(*) FROM `task`
WHERE `company_id` = ? AND `status` = 'COMPLETED' AND `is_late` = 1;
```

**详情接口的完整口径**（`TaskService.detail`，v1.3 统一）：

```
requireTask(id) → requireCompany(companyId) → requireMember(companyId)   -- 不存在 404 / 已解散 409 / 非成员 403
再判定：系统管理员 或 本公司创始人·管理者 → 直接放行
        否则 → taskMapper.canView(taskId, me) 不通过 → 403「无权查看该任务」
```

即：**列表口径 ⊆ 详情口径必须成立** —— 列表里看得见的任务，详情必须点得进去（v1.3 修复前管理者会在这里吃 403）。`canView` 里的 `publisher_id` 分支与"发布者也是管理者/创始人"这条现实重叠，属于防御性条件，与 3.4 的措辞保持一致。

### 7.12 主动退出公司（M-13）

```sql
UPDATE `user_company`
SET `status` = 0, `leave_type` = 1, `left_at` = NOW()
WHERE `user_id` = ? AND `company_id` = ? AND `status` = 1;
```

```
1. 校验公司存在（不存在 404）
2. 查我在该公司的在职角色 → null（非在职）→ 403「你不是该公司成员」
3. 角色为 FOUNDER → 409「创始人不能退出公司，请先解散公司」
4. 执行上面的 UPDATE，影响 0 行 → 409（并发下已被移除/已退出）
```

**与 7.9（被移除）、7.8（被拉黑）是同一套写法的第三种**：都用 `status = 1` 做条件、都写 `leave_type` 与 `left_at`，区别只在 `leave_type` 的取值（1 / 2 / 3）。三种离职方式的可区分性由此闭合（见 6.18）。设计理由：**创始人不允许退出**，必须走 7.10 解散公司。

> 退出后该用户的可见范围立即收窄：列表与详情都要求"当前在职成员"（见 10.1 Q9），因此退出后看不到该公司的任何任务，但 `user_company` 的历史行、`join_application` 的历史、以及任务本身的留痕都还在（T-10 不做物理删除）。再次凭邀请码申请通过时，会复用原成员行（7.7 的 `upsertOnApprove`）。

## 8. 接口设计草案

> 统一前缀 `/api`。除注册登录外均需鉴权（`Authorization: Bearer <token>`）。
> 统一响应包装：`{ code, message, data }`，`code = 0` 成功，非 0 为语义错误码（400/401/403/404/405/409/429/500）。**HTTP 状态码恒为 200**，错误只看响应体的 `code`（原因与契约见 6.16）。
> **本章的「路径 + HTTP 方法」与后端实现（v1.3，`mvn compile` + `mvn test` 通过）逐条核对一致；请求体与响应体的字段以 `dto/` 下的 DTO 为准，本章不逐一列出。**
> 除特别注明外，接口均要求「当前用户是该公司在职成员」，公司已解散一律拒绝（409）。

### 8.1 认证

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/register` | 手机号注册（不写 system_role，数据库默认 USER） |
| POST | `/api/auth/login` | 登录，返回 JWT token 与用户信息 |
| GET | `/api/auth/me` | 当前用户信息（含系统角色，前端据此切页面） |
| PUT | `/api/auth/me` | 修改自己的昵称 |

**认证实现**：自研 JWT（jjwt 0.12.6）+ Spring 拦截器。令牌只携带用户 ID，拦截器每次请求从数据库现查用户状态与角色（禁用、改角色立即生效）。密码用 BCrypt（仅引入 `spring-security-crypto`，不引入完整 Spring Security）。未选 Sa-Token 的原因：Spring Boot 4.1.1 过新，第三方 starter 兼容性无保证。

## 附录：设计原则速查

本项目在数据库设计中反复使用以下原则，新增功能时可参照：

1. **推导出来的事实不手工维护** —— 用生成列（`founder_only` / `pending_only` / `is_late`）
2. **生命周期不同 → 独立成表**；只是用途不同 → 加类型列（对比 6.2/6.3 与 6.9）
3. **正确性问题交给数据库，频率问题交给业务层**（6.6）
4. **并发靠条件 UPDATE + 行锁，不靠先查后写**（6.7）
5. **MySQL 没有部分唯一索引 → 生成列 + 唯一索引**（6.4）
6. **单表多个外键指向同一张表时，约束名必须不同**

> **v1.3 补充（对第 3 条的修正）**："频率问题交给业务层"**不等于"不需要并发保护"**。「每天最多 3 次申请」仍然要靠数据库行锁把同一用户串行化（6.17，`SELECT ... FOR UPDATE`）—— 改变的只是手段（不用触发器，改用行锁），"先查后写必须配并发保护"这条原则不变。
